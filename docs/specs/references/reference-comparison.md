## Navbar

Reference:
`https://zalt.me/`

Reason:
The navbar should follow the `zalt.me` pattern because it is the strongest reference for combining identity, navigation, and action in a single header. It gives the site an immediate personal signature through the brand area, keeps the main sections easy to scan, and reserves space for a clear primary call to action. This works better for the project than a more reduced portfolio navbar, because the site needs to guide visitors toward both content and contact, not only present a minimal visual frame.

Why Not Other References:
`santifer.io` is more narrative and compressed, which weakens quick orientation in the header. `brittanychiang.com` is elegant but too sparse for a navbar that needs stronger section clarity and call-to-action support. `mattfarley.ca` is more CTA-driven than section-driven, so it is less useful as the base navigation pattern for this project.

## Hero Section

References:
`https://santifer.io/`
`https://zalt.me/`

Reason:
The hero section should primarily follow `santifer.io` because it provides the clearest model for a sharp, expertise-driven introduction. Its structure communicates identity and specialization quickly, which makes the landing experience feel deliberate instead of generic. With a one borrowed trait from `zalt.me`: a clearer CTA area.

Why Not Other References:
`zalt.me` works better as a more commercial and conversion-oriented hero, but it is less precise than Santifer for an expertise-first introduction. `harshvora.dev` is clear, but its hero feels more conventional and less distinctive, which makes it weaker for the tone this project is aiming for.

## Experience

References:
`https://santifer.io/`
`https://brittanychiang.com/`
`https://jrdan.dev/`

Reason:
The Experience section should use `santifer.io` as the visual base, while borrowing the role-first information hierarchy seen in more structured experience sections such as `brittanychiang.com` and `jrdan.dev`. This is a plausible middle ground because `santifer.io` offers the most modern and distinctive presentation style, but its experience entries do not follow a single rigid content standard across all cases. For this project, the section should keep the visual character and layout direction of Santifer while applying a more consistent structure: company logo, experience title as the main heading, company name as secondary text, supporting context such as period, and a concise description followed by related project summaries. This approach stays aligned with current portfolio conventions because it combines a modern editorial surface with a clearer and more scannable content hierarchy.

Why Not Other References:
`brittanychiang.com` is stronger for a strictly chronological work-history section, but it is too restrained to serve as the full visual base for this site. `jrdan.dev` is useful for clearer repeatable structure, but it is visually more conventional than Santifer. `bojidaryovchev.dev` is informative, yet too dense and resume-like for the concise experience format chosen here. `zalt.me` emphasizes proof and service breadth more than a clean experience narrative. `aidanm.com` is broader and more expansive, but gives the section more weight than the homepage structure should carry.

## Projects

References:
`https://santifer.io/`
`https://jrdan.dev/`

Reason:
The Projects section should use `santifer.io` as the visual base while applying a `jrdan.dev`-like structure to each item. This is the most suitable direction because Santifer provides a more modern and editorial presentation style, which keeps the section aligned with the rest of the website, while Jrdan offers a clearer and more repeatable content hierarchy for project entries. For this project, each item should follow a stable structure based on the available resume data: project title, year, summary, bullets, links, and skills. This makes the section visually expressive without losing consistency, and it supports projects that need more substance than a minimal portfolio card can provide.

Why Not Other References:
`jrdan.dev` alone would provide structure, but it is not as strong as Santifer as the main visual identity reference for the site. `zalt.me` is powerful for larger project archives, but it is too database-like and heavy for the homepage projects section. `brittanychiang.com` is disciplined and elegant, but more minimal than the richness of the project content deserves. `mattfarley.ca` is more commercial and showcase-oriented, which is less suitable for the broader project detail this portfolio contains. `harshvora.dev` and `bojidaryovchev.dev` are clearer in a resume-like way, but they do not provide the same modern editorial balance.

## Skills and Languages

References:
`https://santifer.io/`

Reason:
The Skills section should follow `santifer.io` because it presents capabilities in a compact and modern way that feels integrated with the rest of the site instead of isolated as a technical inventory. ## Closing Contact Block

References:
`https://santifer.io/`
`https://zalt.me/contact`

Reason:
This part of the homepage should not become a large standalone Contact section or a card-based contact grid. The most suitable direction for the project is a compact closing block that works as the final page ending while keeping contact visible without giving it disproportionate weight in the overall structure. This choice is better aligned with the current amount of contact data and with the broader direction of the site, which is favoring concise and integrated sections. `santifer.io` provides the best base for this lightweight closing treatment, while `zalt.me/contact` offers the clearest model for how each contact method can be presented as a labeled action instead of only as an icon. This creates a stronger middle ground for the project: more explicit and usable than icon-only links, but still lighter and more consistent than a large dedicated contact module.

Why Not Other References:
`brittanychiang.com` supports a lighter social treatment, but icon-only links would be too weak for the importance of email and professional profiles in this site. `mattfarley.ca` gives contact more standalone weight, which is unnecessary for the current amount of contact data. `bojidaryovchev.dev` also leans toward a more explicit sectioned contact treatment, but that would make the homepage ending heavier than needed. A card-based pattern like the one considered from `codebyluis.dev` would likely overstate the contact block and break the compact closing rhythm chosen for the site.
